### ЭТАП 1. ПРОЕКТИРОВАНИЕ И АРХИТЕКТУРА

#### 1. Ролевая модель доступа (RBAC) и матрица прав
В системе формализовано 5 ролевых групп с жестким разделением привилегий:
1. **Гость (`guest`):** Неавторизованный пользователь. Доступен просмотр публичных страниц и каталога репетиторов.
2. **Ученик / Клиент (`student`):** Поиск репетиторов, запись на занятие, оплата урока, доступ в личный кабинет, участие в видеоуроке, отправка сообщений в чат, публикация отзывов.
3. **Репетитор / Сотрудник (`tutor`):** Настройка ставки и резюме, просмотр расписания в календаре, проведение видеоуроков, чат с учеником.
4. **Администратор (`admin`):** Просмотр списка пользователей, принудительный отзыв сессий, модерация/удаление отзывов, смена паролей учеников и репетиторов.
5. **Супер-администратор / Владелец (`owner`):** Абсолютный контроль системы. Единственная роль, имеющая право назначать роли и менять пароли администраторов.

```text
Матрица доступа:
+───────────────────────────+───────+─────────+────────+───────+───────+
| Операция / Маршрут        | Гость | Студент | Тьютор | Админ | Овнер |
+───────────────────────────+───────+─────────+────────+───────+───────+
| Просмотр каталога         |  ДА   |   ДА    |   ДА   |  ДА   |  ДА   |
| Запись на урок            |  НЕТ  |   ДА    |  НЕТ   |  НЕТ  |  НЕТ  |
| Оплата своего урока       |  НЕТ  |   ДА    |  НЕТ   |  НЕТ  |  НЕТ  |
| Вход в видеокомнату урока |  НЕТ  |  Участн | Участн |  НЕТ  |  НЕТ  |
| Чат урока                 |  НЕТ  |  Участн | Участн |  НЕТ  |  НЕТ  |
| Доступ к /admin           |  НЕТ  |   НЕТ   |  НЕТ   |  ДА   |  ДА   |
| Отзыв сессий других польз.|  НЕТ  |   НЕТ   |  НЕТ   |  ДА   |  ДА   |
| Смена пароля админа       |  НЕТ  |   НЕТ   |  НЕТ   |  НЕТ  |  ДА   |
+───────────────────────────+───────+─────────+────────+───────+───────+
```

Иерархия управления паролями реализована в методе `can_manage_user` (`models.py`):
```python
def can_manage_user(self, target_user):
    if self.role == 'owner':
        return True
    if self.role == 'admin':
        if target_user.id == self.id:
            return True
        return target_user.role not in ('admin', 'owner')
    return False
```

#### 2. Проектирование схемы базы данных PostgreSQL
База данных содержит 8 нормализованных таблиц (3НФ):
* `users` — учетные записи (id, email, password_hash, role, `_phone` [зашифрован], created_at).
* `tutor_profiles` — профиль преподавателя (id, user_id [FK ON DELETE CASCADE], subject, hourly_rate, bio, experience_years).
* `lessons` — занятия (id, tutor_id [FK], student_id [FK], date, duration_minutes, status, meeting_link).
* `reviews` — отзывы (id, tutor_id [FK], student_id [FK], lesson_id [FK], rating, comment, is_moderated, created_at).
* `chats` — комнаты чатов для конкретного урока (id, lesson_id [FK ON DELETE CASCADE], created_at).
* `chat_messages` — сообщения чата (id, chat_id [FK ON DELETE CASCADE], sender_id [FK], message, created_at).
* `payments` — финансовые проводки (id, lesson_id [FK], payer_id [FK], amount, status, `_transaction_ref` [зашифрован], created_at).
* `user_sessions` — журнал авторизованных сессий (id, user_id [FK], token, ip_address, user_agent, is_active, created_at, expires_at).

#### 3. Выделение полей, подлежащих шифрованию (152-ФЗ)
* `users._phone` — номер телефона клиента/репетитора. Персональные данные. Хранятся в виде зашифрованного Base64 токена.
* `payments._transaction_ref` — уникальный идентификатор банковской транзакции. Конфиденциальные финансовые данные.
* `users.password_hash` — учетные данные. Хранятся в виде криптографического соленого хеша.

### ЭТАП 3. РЕАЛИЗАЦИЯ МЕХАНИЗМОВ ЗАЩИТЫ (ЯДРО ИБ)

#### 1. Криптографическое хеширование паролей с солью
Используется алгоритм **PBKDF2-HMAC-SHA256** через библиотеку Werkzeug:
```python
# models.py
def set_password(self, password):
    # Автоматически генерирует криптографическую соль и производит 260 000+ итераций хеширования
    self.password_hash = generate_password_hash(password)

def check_password(self, password):
    return check_password_hash(self.password_hash, password)
```
Даже если два пользователя зарегистрируются с одинаковым паролем `password123`, их хеши в БД будут абсолютно разными благодаря уникальной псевдослучайной соли.

#### 2. Симметричное шифрование «на лету» (Fernet / AES-128-CBC)
Модуль `encryption.py` реализует симметричное шифрование стандарта Fernet:
```python
# encryption.py
from cryptography.fernet import Fernet
from config import Config

fernet = Fernet(Config.ENCRYPTION_KEY.encode())

def encrypt_data(data: str) -> str:
    if not data:
        return ""
    return fernet.encrypt(data.encode('utf-8')).decode('utf-8')

def decrypt_data(data: str) -> str:
    if not data:
        return ""
    return fernet.decrypt(data.encode('utf-8')).decode('utf-8')
```

В модели `User` применен паттерн **Transparent Property Encryption**:
```python
# models.py
_phone = db.Column('phone', db.String(256))

@property
def phone(self):
    return decrypt_data(self._phone)

@phone.setter
def phone(self, value):
    self._phone = encrypt_data(value)
```
Разработчик маршрутов обращается к обычному свойству `user.phone`, а физически в таблицу `users` всегда записывается Base64-криптограмма. При дампе базы злоумышленник не получит телефоны пользователей.

#### 3. Сессионная безопасность: 5-минутные токены и принудительный отзыв
В `config.py` установлен короткий таймаут сессии (`PERMANENT_SESSION_LIFETIME = timedelta(minutes=5)`). В БД создается запись `UserSession` с уникальным токеном `secrets.token_urlsafe(32)`.

На каждый HTTP-запрос срабатывает перехватчик `@app.before_request`:
```python
@app.before_request
def validate_session():
    if request.endpoint in ('static', 'logout', 'login', 'register'):
        return

    if current_user.is_authenticated:
        token = session.get('auth_token')
        if not token:
            logout_user()
            return redirect(url_for('login'))

        user_sess = UserSession.query.filter_by(token=token).first()
        # Проверка 1: существует ли запись и не отозвана ли сессия администратором
        if not user_sess or not user_sess.is_active:
            logout_user()
            flash('Ваша сессия была завершена администратором.', 'danger')
            return redirect(url_for('login'))

        # Проверка 2: не истекли ли 5 минут
        if user_sess.is_expired():
            user_sess.is_active = False
            db.session.commit()
            logout_user()
            flash('Срок действия токена авторизации (5 минут) истек.', 'info')
            return redirect(url_for('login'))
```
Администратор в панели управления видит все активные сессии и по нажатию кнопки может отозвать любую из них (`/admin/sessions/<id>/revoke`), что мгновенно разлогинивает пользователя при следующем запросе.

#### 4. Двухконтурная защита от Stored XSS (bleach + Jinja2)
Пользовательский ввод в чатах и отзывах фильтруется перед записью в БД:
```python
# app.py: Чат урока
safe_content = bleach.clean(
    form.content.data,
    tags=[],        # Полный запрет любых HTML-тегов (<script>, <iframe>, <img> и др.)
    strip=True      # Удаление запрещенных тегов из строки
)
msg = ChatMessage(chat_id=chat.id, sender_id=current_user.id, message=safe_content)
db.session.add(msg)
db.session.commit()
```
Второй контур — шаблонизатор Jinja2, который при выводе `{{ msg.message }}` автоматически заменяет спецсимволы `<`, `>`, `&` на соответствующие HTML-сущности (`&lt;`, `&gt;`, `&amp;`).

#### 5. Защита от манипуляций со стоимостью урока (Price Tampering)
В онлайн-системах частой уязвимостью является изменение цены через панель разработчика (F12) в скрытом поле `<input name="amount" value="1500">` на `1`.
В проекте реализована серверная перепроверка:
```python
# app.py: Маршрут /pay/<lesson_id>
expected_amount = lesson.tutor.hourly_rate
submitted_amount = float(form.amount.data)

# Сверка с эталонным тарифом в БД
if abs(submitted_amount - expected_amount) > 0.01:
    flash('Попытка фальсификации стоимости услуги! Транзакция заблокирована.', 'danger')
    return redirect(url_for('calendar_view'))

# Генерация безопасного ID транзакции и шифрование
transaction_id = secrets.token_urlsafe(32)
payment = Payment(lesson_id=lesson.id, payer_id=current_user.id, amount=expected_amount)
payment.transaction_ref = transaction_id  # Fernet шифрование
db.session.add(payment)
```

#### 2. Программа тестирования информационной безопасности (Пентестинг)
Проведены целенаправленные попытки взлома системы:

1. **Тест на Stored XSS в чате:**
   - *Вектор:* Ввод строки `<script>alert('HACKED')</script>` в сообщение чата.
   - *Результат:* Функция `bleach.clean` полностью вырезала теги `<script>`. В БД и на экране отобразилась безопасная строка `alert('HACKED')`. Код не выполнился. **Уязвимость закрыта.**
2. **Тест на Stored XSS через обработчики событий:**
   - *Вектор:* Ввод строки `<img src=x onerror=alert(document.cookie)>` в поле отзыва.
   - *Результат:* Тег `<img>` удален, опасный JavaScript нейтрализован. **Уязвимость закрыта.**
3. **Тест на SQL-инъекцию (SQLi):**
   - *Вектор:* Ввод в поисковую строку `' OR '1'='1'; --` и `' UNION SELECT * FROM users; --`.
   - *Результат:* ORM SQLAlchemy преобразовала ввод в строковый литерал параметра `ILIKE '%'' OR ''1''=''1''; --%'`. База вернула пустой список, синтаксической ошибки СУБД не возникло. **Уязвимость закрыта.**
4. **Тест на обход авторизации (Broken Access Control / IDOR):**
   - *Вектор:* Попытка прямого перехода неавторизованным пользователем или студентом по адресу `/admin` и `/admin/users/1/delete`.
   - *Результат:* Сервер прервал выполнение запроса с кодом ошибки `403 Forbidden`. **Уязвимость закрыта.**
5. **Тест на Price Tampering:**
   - *Вектор:* Изменение значения поля формы `amount` с 1500.0 на 1.0 через Chrome DevTools.
   - *Результат:* Сервер обнаружил расхождение более 0.01 руб., отклонил транзакцию и вывел предупреждающее флеш-сообщение. **Уязвимость закрыта.**
6. **Тест на CSRF:**
   - *Вектор:* Отправка POST-запроса на удаление отзыва без токена `csrf_token`.
   - *Результат:* Flask-WTF вернул ошибку `400 Bad Request: The CSRF token is missing`. **Уязвимость закрыта.**
